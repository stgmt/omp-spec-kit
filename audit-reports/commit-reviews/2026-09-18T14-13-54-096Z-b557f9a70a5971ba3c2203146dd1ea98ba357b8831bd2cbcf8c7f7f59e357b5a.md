### Confirmed findings

#### Finding 1: Scenario-authoring design review gate bypass via Gherkin keyword and syntax evasion (Example, Scenario Template, tab indentation)
- **Priority**: P1
- **File path**: `src/authoring/design-review.js`
- **Line range**: 2-21 (also touches `src/enforcement/classifier.js`: 16-36)
- **Observed behavior**: `SCENARIO_HEADER_RE` (`/^[ ]*Scenario(?: Outline)?:/mu`) in `src/authoring/design-review.js` and `FEATURE_SCENARIO_PATTERN` in `src/enforcement/classifier.js` strictly match leading ASCII spaces (0x20) and only the keywords `Scenario:` and `Scenario Outline:`. Standard Gherkin keyword aliases (`Example:`, `Scenario Template:`) and tab indentation (`\tScenario:`) return `false` from `hasScenarioHeader()` and `featureTextHasScenario()`. Consequently, `validateDesignReviewForChanges()` determines `required: false`, allowing `spec_patch` to apply executable test scenarios without a `designReview` payload.
- **Expected behavior**: The design review gate and host preflight classifier MUST intercept and require a valid `designReview` (schema `omp-spec-kit/design-review@1`) for ANY modification to a `.feature` document that introduces or modifies executable scenarios in Cucumber-js, including scenarios defined with standard Gherkin keywords (`Example:`, `Scenario Template:`) and tab indentation (`\tScenario:`).
- **Trigger scenario**: An agent or caller submits a `spec_patch` MCP call targeting a `.feature` document with operations containing `  Example: unreviewed scenario\n    Then step\n` or `\tScenario: unreviewed scenario\n    Then step\n` without supplying a `designReview` object. Both `classifyMcpToolCall` and `ProposalCompiler.compile` accept the patch and commit it to disk without requiring a design review.
- **Impact**: Complete bypass of the scenario-authoring governance and engineering-anti-bike anti-fake-green verification gate. An author or AI agent can introduce arbitrary unreviewed executable BDD test scenarios into `.feature` files without satisfying the mandatory boundary, evidence, alternatives, and `selfTestCheck` mutation proof requirements.
- **Repository evidence**:
  - `src/authoring/design-review.js:3`: `SCENARIO_HEADER_RE = /^[ ]*Scenario(?: Outline)?:/mu` matches only leading spaces and explicit `Scenario` / `Scenario Outline` keywords.
  - `src/enforcement/classifier.js:16`: `FEATURE_SCENARIO_PATTERN = /^[ ]*Scenario(?: Outline)?:/mu` mirrors the identical restrictive regex in host preflight.
  - `package.json:42`: `@cucumber/cucumber 13.2.1` utilizes `@cucumber/gherkin`, which parses `\tScenario:`, `Example:`, and `Scenario Template:` into valid, executable pickle AST nodes.
  - Runtime node execution proof: `validateDesignReviewForChanges(undefined, [changeExample])` returns `{ ok: true, required: false }` and `compile` accepts the unreviewed scenario patch without a `designReview` payload.
  - Runtime node execution proof: `src/kernel/parsers/gherkin.js` `parseGherkinDocument` also drops `Example:` and `\tScenario:` (0 scenarios extracted, 0 diagnostics), making such scenarios untracked in the spec graph while fully executable by cucumber-js.

#### Finding 2: Host preflight tool classifier bypass for camelCase feature byte operations (deleteDocument and renameDocument)
- **Priority**: P2
- **File path**: `src/enforcement/classifier.js`
- **Line range**: 19-78
- **Observed behavior**: `FEATURE_BYTE_OPS` is defined with only snake_case strings (`delete_document`, `rename_document`). When an MCP tool call uses camelCase kinds (`deleteDocument`, `renameDocument`), which are explicitly supported and normalized by `ProposalCompiler.normalizeOperation`, `FEATURE_BYTE_OPS.has(op.kind)` evaluates to `false`. This causes `featurePatchNeedsDesignReview` to return `false` and `classifyToolCall` to return `{ action: "allow" }` instead of blocking with `DESIGN_REVIEW_REQUIRED`.
- **Expected behavior**: `featurePatchNeedsDesignReview` in `classifier.js` must account for camelCase operation kinds (`deleteDocument`, `renameDocument`) or normalize `op.kind` prior to checking `FEATURE_BYTE_OPS`, matching `ProposalCompiler`'s `normalizeOperation` contract so that preflight hook interception blocks unreviewed deletions and renames.
- **Trigger scenario**: An agent issues an MCP tool call to `mcp__omp_spec_kit_spec_patch` with operations: `[{ kind: "deleteDocument", document: "plugin-distribution.feature" }]` on a spec containing scenarios. The host preflight classifier allows the call instead of blocking with `DESIGN_REVIEW_REQUIRED`.
- **Impact**: Bypasses host-level preflight tool call classification (`classifyToolCall` / `classifyMcpToolCall` in the OMP extension `tool_call` hook). While the MCP server's internal `ProposalCompiler` normalizes the operation and eventually rejects it, the defense-in-depth preflight gate fails to block the call before execution as required by the extension architecture contract.
- **Repository evidence**:
  - `src/enforcement/classifier.js:19`: `const FEATURE_BYTE_OPS = Object.freeze(new Set(["delete_document", "rename_document"]))`
  - `src/enforcement/classifier.js:77`: `if (FEATURE_BYTE_OPS.has(op.kind) && spec !== "" && featureFileHasScenario(root, spec, document)) return true`
  - `src/authoring/proposals.js:62`: `ProposalCompiler` normalizes camelCase `op.kind` (`deleteDocument` -> `delete_document`) via `normalizeOperation`.
  - Runtime node execution proof: `classifyToolCall` returns `{ action: "allow" }` for `deleteDocument` on scenario-bearing feature files, whereas `delete_document` correctly returns `{ action: "block", code: "DESIGN_REVIEW_REQUIRED" }`.
