### Confirmed findings

**[P1] correctness-1 — designReview declared only on the spec_patch `patch` variant: archiveSpec/deleteSpecDoc/renameSpecDoc/createSpec intents can never satisfy the new scenario gate**
- File: src/adapters/tool-contracts.js:336-337 (also :396-399, :747, :782-796)
- Observed: optionalField("designReview","json") exists only in the `patch` variant. archiveSpec has fields:[]; deleteSpecDoc/renameSpecDoc/createSpec declare no designReview. validateContractArguments rejects designReview on those variants with INVALID_REQUEST 'field designReview belongs to another variant' on both transports (mcp/server.js:237, service/dispatch.js:179). Yet the server gate demands it: archive_spec calls validateDesignReviewForChanges (proposals.js:587), deleteSpecDoc/renameSpecDoc compile to delete_document/rename_document ops hitting the patch-path gate (proposals.js:808), and createSpec writes `<spec>.feature` from the title (proposals.js:489). The classifier preflight only inspects input.operations, which facade intents never carry, so it fail-opens to the unreachable server gate.
- Expected: every spec_patch intent whose compiled changes can touch a scenario-bearing .feature document must accept designReview (variant field or commonFields), so DESIGN_REVIEW_REQUIRED is satisfiable through the declared tool surface.
- Trigger: spec_patch intent=archiveSpec on a spec whose <slug>.feature contains 'Scenario:' → DESIGN_REVIEW_REQUIRED without designReview; retry with designReview → INVALID_REQUEST 'field designReview belongs to another variant, not archiveSpec'. Identical deadlock for deleteSpecDoc/renameSpecDoc on a scenario .feature, and createSpec with a title embedding newline + 'Scenario:'.
- Impact: archiving, deleting, or renaming any scenario-bearing .feature document through the documented facade intents is permanently refused — the gate is unsatisfiable for exactly the operations it targets; only raw intent=patch with an operations array can pass a review.
- Evidence: tool-contracts.js:336,396-399,747,782-796; proposals.js:353-367,481-491,587,808; mcp/server.js:237; service/dispatch.js:179; classifier.js:47-60.

**[P2] security-1 — featureFileHasScenario joins unvalidated spec/document into a read path: .feature existence/content oracle outside .specs**
- File: src/enforcement/classifier.js:37-45
- Observed: featureFileHasScenario builds filePath = path.join(root, '.specs', spec, document) and readFileSync's it. spec (input.spec) and document (op.document/op.doc) come straight from raw tool_call input with no isValidSpecSlug/isCanonicalDocument check; the classifier runs pre-dispatch, before any contract validation. path.join resolves '..' segments, so spec='../../..' or document='../../x.feature' escapes .specs; document needs only a case-insensitive .feature suffix.
- Expected: the enforcement layer should validate the probe path the way the server does (isCanonicalDocument rejects '..', absolute paths, empty segments — transactions.js:35-54) before any filesystem access.
- Trigger: spec_patch intent=patch, spec='../../../other-repo/.specs/secret-spec' (or document='../../../../outside.feature'), operations=[{kind:'delete_document', document:'plan.feature'}]: if the resolved file exists and contains a Scenario: header outside docstring fences the call is blocked with DESIGN_REVIEW_REQUIRED, otherwise allowed — a boolean oracle for existence + content-class of any readable *.feature file; read errors fail open so the oracle is reliable for existing files.
- Impact: information-disclosure oracle across the .specs trust boundary inside the enforcement component itself — an agent caller can probe arbitrary .feature-suffixed paths anywhere the OMP process can read.
- Evidence: classifier.js:38-45,47-60 (staged); transactions.js:35-54 (server-side validation runs post-dispatch, cannot defend the hook); enforcement/adapter.js + v0.1/extension.js (pre-dispatch wiring).

**[P2] security-2 — definition-integrity multiset masks deepening a DUPLICATE_DEFINITION group: per-group diagnostic keeps an identical identity key**
- File: src/authoring/proposals.js:763-797
- Observed: diagnosticIdentity keys gated diagnostics as code\0span.path\0(canonicalId ?? actual ?? message). DUPLICATE_DEFINITION is emitted once per canonicalId group (build.js:325-338, processedGroups) with span = ordered[0] per compareCandidateSpans (path, then startOffset). Adding a third duplicate that sorts after the current primary keeps the same primary span and canonicalId → identical key, count 1→1 → afterCounts <= beforeCounts → gate passes.
- Expected: the gate's contract is rejecting net-new malformed definitions; a new duplicate heading is a new violation even when the diagnostic is group-level. Identity should incorporate group.count or relatedSpans.
- Trigger: corpus already has FR-1 defined twice (WARNING, graph stays valid). Proposal appends a third '## FR-1:' heading later in the same document (or in any doc whose path sorts after the primary's). The diagnostic keeps the same span/canonicalId → same multiset key → no introduced findings → patch applies with three ambiguous definitions.
- Impact: the new write gate silently permits proposals that deepen an existing DUPLICATE_DEFINITION violation — the malformed-definition class it was added to prevent — whenever a pre-existing duplicate exists and the new candidate doesn't displace the primary span.
- Evidence: build.js:325-338,727-731; proposals.js:763-767,782-797; tests/authoring-write-gate.test.mjs (count-swap covered; group-deepening not covered).
