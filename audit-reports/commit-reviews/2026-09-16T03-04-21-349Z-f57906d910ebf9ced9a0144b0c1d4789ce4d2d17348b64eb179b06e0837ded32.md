### Confirmed findings
- **Finding ID**: correctness-2
- **Priority**: P2
- **Defect Class**: correctness
- **File**: src/service/versioned.js
- **Line Range**: 107-133
- **Observed Behavior**:
  `createVersionedReads` passes `args.doc` directly to `git.show(row.commitSha, docPath)` without verifying whether the target is a text document or regular file. For directory paths within a spec (e.g. `diagrams`, `assets`), `git.show` exits with code 0 and emits Git's internal tree object listing (`tree <sha>:<docPath>\n\n<entries>`), which `versioned.js` packages into a `kind: "document"` success envelope with computed sha256 and line count. For non-text/binary files, raw bytes are returned as UTF-8 text documents without validating `TEXT_EXTENSIONS` (`.md`, `.feature`, `.json`). Additionally, when a requested document does not exist, line 110 returns error code `DOCUMENT_NOT_FOUND` instead of canonical `DOC_NOT_FOUND` used across the codebase (`src/adapters/document-service.js:122,179`, `src/authoring/transactions.js:122`, `tests/helpers/evidence-e2e.mjs:291`).
- **Expected Behavior**:
  Versioned document reads under `action: "read"` must validate that `args.doc` has a valid text extension matching canonical `TEXT_EXTENSIONS` (`.md`, `.feature`, `.json`) and is a regular file, rejecting directories and non-text files with error code `DOC_NOT_FOUND`. When a document is missing in the published snapshot commit, the service must return canonical error code `DOC_NOT_FOUND` rather than `DOCUMENT_NOT_FOUND` to preserve protocol compatibility with MCP clients, test suites, and unversioned document handlers.
- **Trigger Scenario**:
  A client invokes `spec_documents` with `{ action: "read", spec: "spec-kernel", doc: "diagrams", version: "1.0.0" }` where `diagrams` is a directory, or with `{ action: "read", spec: "spec-kernel", doc: "missing.md", version: "1.0.0" }`. In the directory case, the call succeeds with an HTTP 200 / success envelope returning internal Git tree listings as document text. In the missing document case, it returns non-canonical `DOCUMENT_NOT_FOUND` instead of `DOC_NOT_FOUND`.
- **Impact**:
  Breaking error-code contract mismatch causes MCP clients, automated workflows, and test assertions expecting `DOC_NOT_FOUND` to misclassify or fail on missing versioned documents. Requests for subdirectories leak internal Git tree structures wrapped in success envelopes, while requests for binary files deliver corrupted UTF-8 text.

### Unproven/rejected summary
- **Candidate correctness-1** (`src/service/publish.js:89-99`): Tag healing masks remote tag divergence and suppresses drift reporting when conflicting remote tag exists.
  - **Disposition**: `rejected` (Triage: `not_applicable`).
  - **Rationale**: The publish pipeline specification (`publish.js:25-33`) specifies: "Rules: same version + same tree → no-op (heals a missing remote tag); same version + different tree → VERSION_EXISTS rejection...". When a spec has an existing ledger row with matching tree digest, the local spec content is identical to the verified published version. The healing branch in lines 88-100 specifically heals missing remote tags (`remoteTagCommit === null`). If an out-of-band tag exists on origin pointing to a different commit, Git rejects the non-forced push, which is caught and logged. Emitting `VERSION_EXISTS` would be incorrect because the ledger already recorded that version at the correct tree, and because `publishAll` runs on every periodic sync reconcile and service startup, emitting a rejection on every tick for already-published specs would flood the access log and drift report with false positives. The ledger is the canonical authority for publication records.
