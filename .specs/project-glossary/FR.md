# Функциональные требования

## FR-1 — Один файл проекта
Кит хранит один авторитетный `GLOSSARY.md` на проект. Файл лежит в репозитории проекта на единой служебной ветке `spec-glossary` по пути `glossary/<owner>/<project>/GLOSSARY.md`; префикс `spec-` выбран потому, что только он попадает под действующую защиту канонических веток. Идентификатор проекта хранится в метаданных файла и сверяется при каждом открытии: несовпадение пути и идентичности — отказ, а не объединение проектов. Если два проекта используют один репозиторий, они имеют разные пути на одной ветке и не видят файлы друг друга. Все спецификации и ветки этого проекта разрешают один и тот же файл; запись в файл конкретной спеки не создаёт общую копию. Каждое чтение возвращает версию содержимого, сохраняемого в истории. Уполномоченный читатель может через MCP запросить историческую версию; для записи спеки принимается только актуальная версия.

## FR-2 — Обнаружение и чтение
Refs: spec-mcp-operations:FR-30
Инструкции MCP при подключении, описание инструмента `spec_glossary`, ссылка в сгенерированном для проекта `AGENTS.md` и отказ при содержательной правке сообщают, что общий глоссарий обязателен, как его найти и прочитать; ссылка в `AGENTS.md` указывает на инструмент и порядок создания, а не дублирует определения. Инструмент `spec_glossary` позволяет узнать состояние, прочитать весь файл с версией и искать каноническое слово или явно указанную форму. Поиск возвращает определение, статус формы и версию файла. Полное чтение большого файла доступно по страницам одной неизменной версии; клиент собирает исходные байты и проверяет SHA-256. При ограничении ответа возвращаются признак усечения и следующий диапазон; частичный ответ не выдаётся за полный.

## FR-3 — Создание и редактирование
Refs: spec-mcp-operations:FR-24, spec-mcp-operations:FR-26
Уполномоченный автор создаёт файл для проекта через `spec_glossary` до первой содержательной правки спеки; создание файла в обход инструмента не поддерживается. Дальнейшее добавление, изменение и удаление терминов проходит через `spec_glossary` с предварительным просмотром, ожидаемой версией содержимого и атомарным применением. Отсутствующий файл не заменяется данными из отдельной спеки или образцом. При неопределённом значении агент не выдумывает его, а фиксирует вопрос и не объявляет термин согласованным.

## FR-4 — Проверка актуальной версии
До содержательного изменения спецификации автор получает текущий файл и передаёт его `contentSha256` в параметре `glossarySha256` существующего `spec_patch` при предварительном просмотре и применении. Сервер проверяет версию повторно непосредственно перед сохранением, согласуя её с конкурирующей записью глоссария через общий механизм взаимоисключения или эквивалентную атомарную проверку. Отсутствие, недоступность или несовпадение версии блокирует изменение без частичной записи и сообщает, как восстановиться. Проверка подтверждает предъявление актуальной версии, а не понимание или прочтение агентом.

## FR-5 — Термины и ошибки
Refs: spec-mcp-operations:FR-31
При проверке кандидатного текста сервер определяет явно перечисленные запрещённые формы, учитывая границы слов и нормализацию, определённые в схеме. Для каждой находит документ и место, форму и каноническую замену. Ненайденный новый термин не считается доказанно корректным: подсказка требует содержательно сверять новые термины с владельцем и обновлять глоссарий перед их употреблением. Ошибки различают отсутствие, недоступность, неподходящую версию, нарушение формата, запрещённую форму и недостаток прав; каждая содержит безопасный следующий шаг.

## FR-6 — Изоляция и разрешения
Чтение и запись учитывают выбранный проект, авторизацию и действующие роли реестра. Отказ за пределами доступа не раскрывает содержимое или существование файла чужого проекта. Историческая ревизия принимается только из защищённой истории ветки `spec-glossary` по пути выбранного проекта с проверенной привязкой, даже если проекты используют одну репозиторию; чужой путь на общей ветке отклоняется так же, как отсутствующий или недоступный файл. Недостаток прав не интерпретируется как отсутствие файла. Предварительный просмотр не создаёт и не меняет ветку, файл или другие постоянные данные. Единственный путь изменения авторитетной ветки — проверенный сервисный путь; обычный пользователь не может обойти MCP прямой записью в эту ветку.

## FR-7 — Состязательные изменения и сбои
Запись с устаревшей версией отклоняется целиком; актуальный источник перечитывается перед повторной правкой. Идемпотентность, повтор по идентификатору и межпроцессная блокировка берутся из существующего `src/authoring/transactions.js` (`withWriteLock`, журнал по `requestId`); второй протокол не проектируется. Ошибки хранилища, сбой сети и конфликт параллельных авторов не дают ложного успеха. Повтор с тем же идентификатором и тем же содержимым не создаёт вторую запись; тот же идентификатор с иным содержимым отклоняется. После одновременной попытки двух сервисов проигравший повторно ищет результат в проверенной истории перед любым повторным применением. Результат различает подтверждённое применение и неизвестный исход; после потери ответа подтверждение ищется в авторитетной истории операции.

## FR-8 — Запуск без циклической зависимости и доставка
Подключение проекта, чтение статуса, помощь и создание первого файла доступны без ранее созданного глоссария; файл не создаётся автоматически при регистрации проекта. До создания файла содержательные правки спецификаций блокируются, чтение существующих спецификаций остаётся доступным. Отказ гейта называет причину и точное действие — `spec_glossary {action:"create"}` — и не предлагает прямую запись в хранилище. Гейт проверяет наличие и валидность файла, а не согласованность терминов: пустая таблица валидна и означает только начальное состояние. После реализации одинаковые правила действуют в локальном и сетевом MCP для зарегистрированного проекта, без отдельного локального режима без реестра, а установленный сервер и подсказки проверяются реальными MCP-вызовами, а не только внутренней функцией.
