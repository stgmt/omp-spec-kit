# Проект решения

Status: DRAFT

## Разделение ответственности
Реестр разрешает проект и проверяет роль; проектное хранилище открывает один файл и проверяет его привязку; ядро разбирает данные и проверяет текст; MCP-поверхность отдаёт инструкции, варианты чтения, поиска и записи, а также ошибки. Существующая проверка готовности включает состояние глоссария, но не выдумывает определения и не создаёт данные. Два отдельных транспорта вызывают одну проверку и один путь записи.

## Хранение и версии
Предлагаемый дизайн: в репозитории, привязанном к проекту, отдельная служебная ветка `project-glossary/<sha256>`, где sha256 — полная SHA-256 точных UTF-8-байтов канонического идентификатора проекта в нижнем регистре шестнадцатеричной записи. Точный идентификатор хранится в метаданных и проверяется: совпадение имени при несовпадении идентичности — отказ, а не объединение проектов. В корне ветки — `GLOSSARY.md` и метаданные, привязывающие точный идентификатор проекта к репозиторию. Привязка проверяется при открытии; неправильная привязка блокирует доступ. Один проект имеет одну такую ветку; метаданные не являются вторым источником терминов. Для нового имени ветки обязательна защита в правилах репозитории: прямой push потребителей запрещён, запись доступна только сервисной учётной записи. Текущие правила для `spec-*` не доказывают защиту ветки с другим префиксом; настройка и отрицательная проверка защиты входят в доставку. Этот вариант требуется реализовать и проверить с общим репозиторием двух проектов и существующими правилами веток; факт его поддержки сейчас не заявляется.

Версия — SHA-256 точных UTF-8 байтов файла. Чтение возвращает байты и версию; история хранит коммиты файла. Авторы не записывают в рабочие деревья напрямую. Предварительный просмотр работает с копией в памяти и не создаёт постоянных данных. Изменение содержит ожидаемую версию; сервер проверяет её в общей защищённой секции перед записью и возвращает новую версию. Идентификатор запроса, идентичность автора, хеш канонического содержимого операции и идентификатор полученного коммита спеки записываются в защищённый коммит проектной ветки без секретов; эта Git-история — авторитет результата. После потери ответа сервис ищет операцию в доступной проверенной истории: тот же автор, идентификатор и хеш возвращают прежний результат; совпадение идентификатора с иным хешем отклоняется. Если доступность и полноту истории нельзя подтвердить, возвращается неизвестный исход, а не фиктивный успех; новые записи по этому идентификатору не выполняются.

## Проектируемый MCP-контракт
Расширить существующие семейства инструментов, не предполагая их наличия сейчас:
- `spec_documents {action:"glossary", mode:"status"|"read"|"search", project, query?, version?, offset?, limit?}`: проект обязателен, если его нельзя однозначно получить из проверенного контекста; имя спеки не передаётся. `query` обязателен только для поиска; `version` разрешён только при чтении и выбирает историческую версию по её идентификатору, отсутствующее поле означает текущую. `read` возвращает закреплённую Git-ревизию, SHA-256, общий размер в байтах, байтовый offset, base64-фрагмент исходных UTF-8-байтов и следующий offset либо конец. Все страницы после первой запрашиваются с той же ревизией; клиент соединяет фрагменты без пропусков, проверяет размер и SHA-256 и лишь затем передаёт этот хеш при авторинге. Усечение и наличие следующей страницы явны; недоступная историческая ревизия даёт ошибку, а не незаметную подмену текущей.
- `spec_patch {intent:"createGlossary"|"replaceGlossary", project, requestId, reason, content, dryRun, expectedSha?}`: `dryRun` по умолчанию true; создание требует отсутствия файла, замена — текущий SHA-256. Применение задаётся `dryRun:false`; идентификатор повторной операции должен сохраняться с результатом. Повтор того же идентификатора с другим содержимым отклоняется как конфликт.
- `spec_inspect {check:"glossary", project, spec?}`: проверяет формат и, при указанной спеке, явные запрещённые формы в её текущих документах; возвращает ошибки с исходными координатами и версию глоссария. Инструкция при подключении и описания инструментов указывают порядок вызовов.
Эти имена действий и поля являются предлагаемым контрактом, а не существующим API; перед внедрением их проверяют на конфликты с действующими контрактами и включают в описания реально установленного сервера. Нельзя скрыть глоссарий внутри фиктивной спеки.

## Допуск содержательных изменений
Первым делом доступна настройка, чтение и создание глоссария. Для содержательного изменения автор передаёт в `spec_patch` поле `glossarySha256` со значением, полученным при полном чтении. Оно обязательно и для обычных операций, и для фасадных команд, создающих или меняющих содержимое. Сервер получает текущую версию, валидирует весь окончательный кандидат и перед фиксацией ещё раз проверяет SHA. Операции с глоссарием и записью спек разных процессов сериализуются в одной репозитории через атомарное изменение Git-ссылок. При каждой записи спеки сервис строит коммит спеки и новый коммит проектной ветки поверх точно прочитанной её головы; дерево глоссария в таком коммите не меняется. Сервер одним атомарным push обновляет обе ссылки, требуя ожидаемые старые головы; изменение глоссария обновляет проектную ветку по тому же правилу. Конкурирующая смена любой головы отклоняет весь push без частичного изменения: клиент перечитывает и выполняет проверку заново. Первое создание спеки также создаёт её ссылку в той же атомарной операции. Прямые изменения защищённых веток вне сервиса запрещены; если удалённый Git не поддерживает атомарный push, защита не установлена, старые головы нельзя подтвердить или репозиторий недоступен, запись блокируется до исправления, без неатомарного запасного пути. Этот дизайн предполагает поддержку сервером Git и должен быть доказан на целевом сервере до реализации. Проектный файл, а не его копия в ветке спеки, определяет действующие слова.

Наличие SHA не доказывает, что человек или модель прочитали или поняли файл. За это отвечают явные инструкции и содержательное ревью, а не фальшивый статус сервера. Операции чтения, настройки и создания первого файла исключены из требования SHA и не образуют цикл. Другие исключения должны быть перечислены до реализации, а не определяться обходной веткой.

## Диагностика
Отдельные машиночитаемые причины: `GLOSSARY_MISSING` (создать), `GLOSSARY_UNAVAILABLE` (восстановить доступ; не подменять пустым), `GLOSSARY_VERSION_REQUIRED` (прочитать), `GLOSSARY_VERSION_CONFLICT` (перечитать и пересмотреть), `GLOSSARY_INVALID` (исправить формат), `GLOSSARY_TERM_FORBIDDEN` (заменить указанную форму). Недостаток доступа использует имеющийся контракт прав без раскрытия других проектов. Эти имена предложены в спецификации и не описывают наличие кода.

## Границы проверки
Проверяются только явно перечисленные запрещённые формы в Markdown-прозе, не блоки/фрагменты кода, адреса ссылок и идентификаторы ссылок; правила схемы обязательны для обеих сторон. Семантические синонимы, словоформы вне списка и корректность определения не обнаруживаются автоматически. Нарушение должно содержать строку и позицию исходного текста, а не нормализованной копии. Подсказки требуют проверки новых терминов автором.

## Незавершённые решения
Проверить предлагаемые имена вариантов MCP на конфликт с действующим контрактом и доказать механизм блокировки и привязки репозитория при нескольких процессах и текущих правилах Git. Реализация и её тесты ещё не существуют; содержащиеся в feature-файле сценарии являются требованиями, а не результатом прогона. Задачи создаются после содержательного согласования корпуса; нельзя подделывать свидетельство проверки.
