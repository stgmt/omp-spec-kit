# Non-Functional Requirements

## NFR-DATA-1 — No divergence without a recorded conflict

Доля переходов, при которых проекция и корпус расходятся без события конфликта, ДОЛЖНА быть равна нулю. Любое расхождение либо применяется, либо фиксируется как `task_sync.conflict`; третьего состояния нет.

## NFR-REL-1 — Atomic canonical writes

Запись задачи в корпус ДОЛЖНА быть атомарной: либо документ обновлён целиком, либо не изменён. Частично записанная задача считается дефектом, а не восстановимым состоянием.

## NFR-PERF-1 — Status transition latency

Смена статуса из UI teams ДОЛЖНА укладываться в p95 ≤ 1500 мс при доступном реестре, включая запись в корпус и обратную проекцию. Операции, не уложившиеся в 5000 мс, ДОЛЖНЫ завершаться тайм-аутом с типизированной ошибкой.

## NFR-SEC-1 — Credentials never leave the main process

Токен реестра ДОЛЖЕН храниться только в main-процессе Electron и НЕ ДОЛЖЕН попадать в renderer, логи, телеметрию и артефакты. Renderer общается с реестром только через IPC-контракт.

## NFR-MAINT-1 — One mapping, no duplicated tables

Маппинг статусов, владение полями и коды ошибок ДОЛЖНЫ существовать в одном исполняемом виде на репозиторий: контракт `contracts/task-sync.contract.json` и генерируемые из него константы. Второй экземпляр таблицы статусов в teams или spec-kit считается дефектом.

## NFR-OBS-1 — Observable sync decisions

Каждое решение синхронизации (создание, обновление, конфликт, отказ) ДОЛЖНО оставлять структурную запись с `operation`, `taskId`, `field`, `decision`, `reason` и не содержать секретов и полного текста задач.

## NFR-COMPAT-1 — Kernel schema stays stable

Расширение модели задач ДОЛЖНО сохранять `spec-kernel@2`: новые поля задачи добавляются как атрибуты существующего узла `TASK`, новые операции — как варианты существующего `spec_patch`. Новый тип узла или новая версия ядра запрещены.

## NFR-TEST-1 — Contract and mapping are BDD-covered

Каждое правило маппинга и каждый код ошибки ДОЛЖНЫ иметь исполняемый сценарий в `.specs/teams-task-sync/teams-task-sync.feature`, запускаемый в CI обеих сторон против одного контракта.
