# Non-Functional Requirements

## NFR-DATA-1 — No divergence without a recorded state

Доля переходов, при которых проекция и корпус расходятся без зарегистрированного состояния (`pending_projection` или `task_sync.conflict`), ДОЛЖНА быть равна нулю. `pending_projection` не ДОЛЖЕН оставаться дольше 5000 мс; иначе он переходит в `task_sync.projection_failed` и видимую ошибку на доске. Третьего состояния нет.

## NFR-REL-1 — Atomic canonical writes

Запись задачи в корпус ДОЛЖНА быть атомарной: либо документ обновлён целиком, либо не изменён. Частично записанная задача считается дефектом, а не восстановимым состоянием.

## NFR-PERF-1 — Status transition latency

Смена статуса из UI teams ДОЛЖНА укладываться в p95 ≤ 1500 мс при доступном реестре, включая запись в корпус и обратную проекцию. Замер ДОЛЖЕН быть end-to-end; отдельно ДОЛЖНЫ записываться длительность реестрового плеча и длительность обновления проекции. Операции, не уложившиеся в 5000 мс, ДОЛЖНЫ завершаться тайм-аутом с типизированной ошибкой.

## NFR-SEC-1 — Credentials never leave the main process

Токен реестра ДОЛЖЕН храниться только в main-процессе Electron и НЕ ДОЛЖЕН попадать в renderer, логи, телеметрию и артефакты. Renderer общается с реестром только через IPC-контракт. `actor` в квитанции ДОЛЖЕН быть аутентифицированным principal из токена; `actorRef` не ДОЛЖЕН использоваться для авторизации или аудита.

## NFR-MAINT-1 — One mapping, no duplicated tables

Маппинг статусов, владение полями и коды ошибок ДОЛЖНЫ существовать в одном исполняемом виде: контракт `contracts/task-sync.contract.json` и генерируемые из него константы. Контракт отдаётся реестром в рантайме; npm-артефакт генерируется из того же файла. Вторая рукописная таблица статусов или владения полями в teams или spec-kit считается дефектом.

## NFR-OBS-1 — Observable sync decisions

Каждое решение синхронизации (создание, обновление, конфликт, отказ) ДОЛЖНО оставлять структурную запись с `operation`, `taskId`, `field`, `decision`, `reason` и не содержать секретов и полного текста задач. Агрегаты ДОЛЖНЫ включать `sync_pending_total`, `sync_pending_age_ms`, `sync_conflict_total`, `status_transition_e2e_ms`; они не заменяют структурные записи.

## NFR-COMPAT-1 — Kernel schema stays stable

Расширение модели задач ДОЛЖНО сохранять `spec-kernel@2`: новые поля задачи добавляются как атрибуты существующего узла `TASK`, новые операции — как варианты существующего `spec_patch`. Новый тип узла или новая версия ядра запрещены.

## NFR-TEST-1 — Contract and mapping are BDD-covered

Каждое правило маппинга и каждый код ошибки ДОЛЖНЫ иметь исполняемый сценарий в `.specs/teams-task-sync/teams-task-sync.feature`, запускаемый в CI обеих сторон против одного контракта. Каждый AC ДОЛЖЕН иметь минимум один тег `@AC-N.M` на сценарии; каждый FR, для которого заявлено покрытие, — минимум один тег `@featureN`. Теги ДОЛЖНЫ резолвиться в `TESTED_BY`; нерезолвленный тег считается дефектом. Для прогона до TASK-1 используется fixture контракта.
