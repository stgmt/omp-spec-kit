# Changelog

## Unreleased — DRAFT

- Initial specification of the centralized spec registry service: dedicated `specs` branch per project, service-only write path, multi-project mounts, remote MCP for agents, YouTrack entry for humans, compose deployment, claims, publish ledger, spec pins.
- **2026-09-13 — model revision**: canonical store changed from per-repo `specs` branches to **one dedicated specs repository** with `<owner>/<project>/.specs/<slug>/` layout (multi-tenant: users → projects → specs). Consumers hold zero repo access; human entry = operator's YouTrack in v1, external YouTrack binding post-v1 via automated onboarding API; metadata store decided as `node:sqlite`; remote MCP transport verified against pinned OMP schema (`type: "http"` + `url` + `headers` + `auth`); omp-spec-kit corpus migration deferred to post-first-release (TASK-14).
- **2026-09-14 — caller context + pin layer removal**: caller context defined as token-derived (`token → tenant → allowed scopes`); `project` is a call parameter with token-default resolution (refused when ambiguous/out-of-scope); `spec` always explicit; **no repo binding in v1**. Consumer pin layer dropped from v1 — `spec-refs.json`, `omp spec verify|outdated|install` deferred to TASK-15 (service is the only read path, so a local pin has nothing to resolve against); R-9 linkage now answered by ledger + registry view; AC-9/UC-6 rewritten as versioned-read integrity; TASK-10 removed from phase 3.
- **2026-09-14 — single access point + official SDK**: dropped the separate `POST /rpc` surface — **all clients (agents + YouTrack app backend) are MCP clients on `POST /mcp`**; the app chain is widget → `host.fetchApp()` → HTTP handler → `http.Connection.postSync` → `/mcp` (verified against YouTrack apps docs: widgets reach external services only through app HTTP handlers; the backend `http` module does outbound POSTs). Service side uses the official `@modelcontextprotocol/sdk` (Streamable HTTP, stateless) + express instead of a hand-rolled adapter; stdio server stays as-is for unmanaged checkouts.
- **2026-09-14 — phase 1 implemented (TASK-3..6)**: `spec-registryd` core landed on `feat/spec-registry-service` — mount manager (one clone, per-project roots, bot-pushed skeletons, boot recovery), `POST /mcp` via the official SDK (stateless, single access point, `spec-kernel@2` with `@1` accepted), write path (token → tenant → claims → kernel apply → bot commit with `Spec-Author:`/`Spec-Request-Id:` trailers, success only after push confirmation), `node:sqlite` store (tenants/claims/ledger/access_log, JSONL fallback), projected `/registry` index, drift report + coalescing sync loop with fast-forward. New deps: `@modelcontextprotocol/sdk@1.30.0`, `express@5.2.1`. Gates: `test:unit` (86+), `test:unit:service` (31), `check:spec-corpus`, `dogfood:mcp` green.
- **2026-09-14 — compose stack (TASK-11, pulled ahead of phase 3)**: `deploy/` — Dockerfile (node:22-slim + git, non-root, `/health` healthcheck), docker-compose (named volume for clone+SQLite, bind-mounted operator config, loopback-only direct port; optional profiles: `git` — in-stack bare repo + git daemon so the stack is fully self-contained, `youtrack` — clean-host YouTrack, `proxy` — nginx-TLS), documented env (`SPEC_REGISTRY_CONFIG/CLONE/STORE/SYNC_MS/BOT_*`). AC-7 verified live on a clean compose project: boot-to-healthy 7.8 s, skeleton created as bot, host read call HTTP 200, write loop `APPLIED` with bot commit on the remote; the `git` profile verified live as well (skeleton pushed to the in-stack daemon). youtrack-sync deferred to TASK-8 (no standalone sweep entrypoint yet).
- **2026-09-14 — YouTrack-backed authN/Z (TASK-12, pulled ahead of TASK-8)**: identity is verified against the live YouTrack, not asserted. Two paths: app bridge (YouTrack app backend secret + `ctx.currentUser` from the verified session, re-checked by the service via `GET /api/users/{login}`) and direct tokens (agent's YouTrack permanent token verified via `GET /api/users/me`; groups always resolved with the service token — Hub field visibility hides a non-admin's own group list). Roles owner/writer/reader from configured role groups gate operations, filter `tools/list`, and make `force` owner-only; claims/trailers/audit carry the verified login; `X-Spec-Author` and envelope `identity` are retired. The service issues and stores no tokens (no `tenants` table); verification cache is in-memory (TTL 60 s); no auth config → refuse to start; YouTrack unreachable → fail-closed `UNAVAILABLE`. **Verified live** end-to-end in the dedicated test compose (`spec-auth-e2e`: real YouTrack completed through the Configuration Wizard, real git daemon, real service) — 12/12 scenarios including browser login and a widget-applied patch landing as a bot commit with the verified `Spec-Author`; `test:service` (17) runs against the same live fixture.
- **2026-09-14 — TASK-14 landed: the corpus migrated through the service, the product repo carries no `.specs/`**: omp-spec-kit's canonical corpus (7 specs, 106 documents) was imported into `stgmt/spec-database` under `stgmt/omp-spec-kit/.specs/` **through the write path** (`createSpec` scaffold → `replace_document` per document, bot commits carrying `Spec-Author`/`Spec-Request-Id`) — no hand-run git against the specs repo. Verified byte-for-byte: 106/106 blobs match the source tree, and the inventory served over MCP matches the code gate (7 specs / 106 documents / 790 nodes / 1378 edges). Code gates no longer read a checkout: they resolve the frozen fixture (`scripts/corpus-root.mjs` — `dogfood:mcp`, release evidence), operator tools fail closed without an explicit corpus root, and `scripts/check-no-root-specs.mjs` (wired into `verify`) enforces the FR-2 boundary. The live corpus is checked through the registry (`npm run check:corpus:remote`: 7 specs / 106 documents / zero error diagnostics). Service-side git access for the private specs repo is now explicit — `SPEC_REGISTRY_GIT_TOKEN` is injected as a URL-scoped `http.extraheader`, never lands in argv/config/responses, and is redacted from git errors; the image gained `ca-certificates` (HTTPS clones were impossible before). Deliberate deviations: history was not replayed (the frozen `specs` branch is stale — 106 files differ) and no consumer clones the specs repo, because the service remains the only git client.
- **2026-09-14 — TASK-7 landed: managed projects run against the registry endpoint**: an OMP-native `omp-spec-kit` definition (project `.omp/mcp.json` or the active profile's user config — `type: "http"` + endpoint + token) is resolved ahead of the plugin's own declaration, because native config precedes extension packages and the first definition wins; the local stdio server is therefore retired for managed projects without changing the shipped payload (the packaging gate keeps asserting stdio). Verified against the pinned OMP runtime: `loadAllMCPConfigs` resolves the native http definition, capability discovery lists `transport: "http"`, and `scripts/probe-managed-remote.mjs` connects through it and calls `spec_catalog` — the registry access log records the call (`alice | writer | spec_catalog | ok`), which is the discriminator against a local server. Template: `config/omp-managed.mcp.json.example`; the plugin README documents managed vs unmanaged and the `NO_PROXY` requirement on proxied hosts (a global HTTP proxy otherwise makes the connection time out after 30 s).
- **2026-09-15 — the app installation path was unspecified; recorded as FR-17 + TASK-16**: nothing in the corpus said how the YouTrack app reaches a customer's instance, while JetBrains documents exactly two paths — **Administration → Apps → Add app… → Browse JetBrains Marketplace** (the app page takes the site URL and opens the install dialog on the site; the app stays marketplace-linked so updates install from YouTrack; requires Low-level Admin Write and Marketplace access) and **Upload ZIP file** (global Update Project or Low-level Admin Write). v1 installs into the operator's own YouTrack, so the convenient path must be the default: the app gets a reproducible build from `tools/spec-graph-app/` checked against the committed ZIP, the release carries the artifact, and the operator flow is one link plus the site URL, with ZIP upload as the private path until the Marketplace listing exists. Installation is verified rather than assumed — the same check the live E2E runs after deploy.
- **2026-09-15 — TASK-16 landed: the app package is CI-built and installs through the official CLI** — one manifest-derived build (`build:youtrack-app`) produces the staged directory + deterministic zip; `verify` runs the official `app validate`; CI publishes the package per push and the release attaches + attests the zip (candidate schema @2, `youtrackApp` digest verified in preflight); the live fixture installs via `youtrack-app app upload` and asserts the installed version; the committed zip, the PowerShell packaging, and the custom upload script are deleted. Gates: unit 123/123, staged 66/66, safe-authoring 26/26, service 23/23, release-integrity 8/8, live e2e 15/15.

- **2026-09-16 — TASK-2 landed: canonical-write protection verified end to end** — service-only writes with bot trailers; foreign-author refusal (FOREIGN_COMMITS, non-retryable); concurrent writes serialize on the project lock with retryable CONFLICT for losers (parallel-write test proves linear bot-only history); break-glass pushes surface as non-bot-commit drift events; new `check:specs-repo` gate asserts the specs repo is private with collaborators limited to owner + service; operator runbook added.

- **2026-09-16 — TASK-9 landed: publish pipeline via immutable git tags** — an authored `Status: ACTIVE` at canonical HEAD publishes an annotated tag `spec/<project>/<slug>/<version>` at the commit plus an insert-only ledger row (version → tree digest → commit); identical content no-ops, different content under an existing version is rejected and surfaces in `GET /drift`; `spec_documents(version)` serves the frozen tagged snapshot with digest re-verified against the commit; triggers on write push, reconcile, and boot.
