# Инструкции — переход на два Gherkin-документа

**Решение владельца от 23.11.2026.** Сценарии спецификаций предназначены для описания поведения. MCP проверяет форму, связи и согласованное покрытие. Запуск сценариев, сбор результатов и обязательный self-test при записи исключены. Упоминания этих механизмов ниже сохраняют контекст первоначального плана.

План рефакторинга и переноса корпуса `omp-spec-kit`. Целевые имена — `<slug>-user-stories.feature` и `<slug>-use-cases.feature`. Команда создания спеки создаёт оба документа. Канон требует эту пару; `<slug>.feature`, `USER_STORIES.md` и `USE_CASES.md` исключены из рабочей схемы записи. Старую спеку можно читать через MCP. При попытке её изменить агент сначала переносит эту спеку; остальные ожидают своей очереди. По состоянию на 24 ноября 2026 путь переноса реализован для локального и hosted MCP; адресные проверки крупных документов приведены в разделе «Проверка больших документов».

## Текущий статус

- Рантайм, авторинг и адресный перенос реализованы. MCP читает старую схему, блокирует запись только в выбранную старую спеку и предоставляет перенос через `spec_patch intent: "migrateSpec"`. Пошаговая инструкция агента передаётся при `initialize`; проверены preview, apply и повтор исходной записи на изолированных stdio и hosted HTTP MCP.
- Поддержка крупных документов проверена на 7,26 МиБ; пределы — 8 МиБ на документ, 20 МиБ на корпус, 24 МиБ на JSON-запрос `/mcp`. Проверены графовые переходы US → FR → TASK и обратный обход к US/UC.
- **Живой MCP пока не готов.** Read-only проверка проекта `stgmt/omp-spec-kit` 24 ноября показала старые пределы 2 МиБ/50 МиБ. `spec_documents includeSnapshot` получил `UNKNOWN_FIELD`, а безопасный `spec_patch dryRun` для старой спеки вернул обычный `PREVIEW`, а не блокер миграции. Применение не запускалось, содержимое не менялось.
- **Осталось:** подготовить следующий minor-релиз, установить его на целевой MCP-хост и повторить smoke-проверку там. Живой корпус не переписывался. Массовая миграция всех старых спек не требуется: перенос запускается адресно при работе с выбранной спекой.

## Целевой контракт

| Документ | Структура и идентичность | Допуск записи |
|---|---|---|
| `<slug>-user-stories.feature` | Один `Feature` на документ. Под ним `Rule` с объявленным `@story:US-N` на каждую историю. Контекст хранится в описании, сценарии в `Scenario` или `Scenario Outline`. | Новая история содержит роль, цель, пользу и хотя бы один полный пример основного результата. ID истории уникален в спеке. Черновой пример с полными Given/When/Then допускается до появления FR и их связей. |
| `<slug>-use-cases.feature` | Один `Feature` на документ. `Rule` с `@case:UC-N` и ровно одним объявленным `@story:US-N` означает кейс. Шаги, ветки и гарантии задаются сценариями и согласованными полями кейса. | MCP разрешает ссылку по ID в итоговой версии этой же спеки. Отсутствующая, повторная или чужая история блокирует запись. Допустимо создать оба объекта в одной атомарной правке. |

Правило принадлежности `SCEN-*` одно на оба файла. У сценария один редактируемый источник и один ID определения. Строки `Examples` могут давать несколько конкретных примеров с этим ID. Когда история и кейс используют один сценарий, второй объект ссылается на его ID. При создании задачи MCP сопоставляет BDD с обязательными исходами именно этой задачи. [Решение о допуске](instructions.md#когда-mcp-блокирует-создание-задачи)

Gherkin разбирает официальный `@cucumber/gherkin`. Типы `USER_STORY`, `USE_CASE` и `SCENARIO` в графе читаются из AST и явных метаданных. Валидация `UC → US` смотрит на тег, объявленный у самого `Rule`, чтобы наследование с уровня `Feature` не подставило одну историю всем кейсам. Грамматика даёт структуру, координаты и текст описания правила. Ядро проверяет поля, идентификаторы и связи из следующего раздела. [Структура Gherkin AST](https://github.com/cucumber/gherkin#abstract-syntax-tree-ast)

`createSpec` создаёт два пустых контейнера `Feature`. Тег `@spec-ready` отмечает сценарий с согласованным покрытием и трассировкой FR/AC. Черновой сценарий проходит проверку формы и ссылок. При создании задачи MCP сверяет описанное покрытие с утверждённой картой исходов. [Допуск задачи](../../src/authoring/bdd-coverage.js)


### Формат пилота

Агент передаёт Gherkin-текст через существующий `spec_patch`. Канонические поля находятся в начале `Rule.description`, перед первым сценарием или `Background`. Ключи полей и порядок столбцов стабильны. Идентификаторы шагов, веток, исходов и строк примеров состоят из строчных латинских букв, цифр и дефисов. Значение может быть на языке автора. Необязательный `Context:` открывает свободный текст после структурированных полей. Полный пример содержит `Given`, `When` и наблюдаемый `Then` в шагах определения. Описание формы и примеры доступны в инструкции инструмента для US и UC.

- **US.** Прямая метка `@story:US-N`, по одной строке `Actor:`, `Goal:`, `Benefit:` и хотя бы один собственный полный пример. Если в исходной истории есть отдельный `Independent Test:`, он сохраняется в одноимённом структурированном поле. При необходимости `Outcome: <id> | <наблюдаемый результат>` объявляет исход истории, на который ссылается карта. `ScenarioRef: <id> | <ссылка>` связывает исход `Outcome` со сценарием.
- **UC.** Прямые метки `@case:UC-N` и `@story:US-N`, по одной строке `Actor:`, `Boundary:`, `Trigger:`, `Precondition:`, `Success:`. `Step: <id> | <действие>` задаёт шаг основного потока. `Branch: <id> | <шаг решения> | <условие> | <наблюдаемый исход> | <выход или шаг возврата>` задаёт путь, включая штатный. Для завершения используется `end`. `ScenarioRef: <id ветки> | <ссылка>` указывает пример этой ветки. Черновик ветки можно сохранить до появления примера. При создании задачи обязательная ветка без примера блокирует допуск.
- **Ссылки.** Цель `ScenarioRef` — `SCEN-*` для обычного сценария или `SCEN-*#<id строки>` для `Outline`. В таблице `Examples` используется столбец `example_id` с уникальными внутри Outline значениями. Разрешены собственные примеры правила и примеры связанного US или его UC в пределах той же спеки. Ссылка из одного UC на сценарий другого UC отклоняется. Для прямых ссылок самой истории или кейса используется `Refs: <slug>:<ID>` в структурированной части `Rule`, до `Context`; это поле создаёт рёбра `REFS` и не заменяет `ScenarioRef`. Текст после `Context` не создаёт неявных связей. Дубли ID, неизвестная цель, ветка без существующего шага и неправильный тег на уровне `Feature` дают ошибку формы. Разделитель столбцов — ` | `. Пустые обязательные значения и лишние столбцы отклоняются.
- **Системный контракт.** `Rule` с прямым `@contract` живёт в `<slug>-user-stories.feature`. Его сценарии имеют действующие связи FR/AC и покрывают явно одобренный системный исход, которому не соответствует пользовательский путь. Карта ссылается на такой сценарий напрямую. Для исхода со связанными US/UC карта использует их объявленную ветку. `@contract`, `@story` и `@case` нельзя совмещать на системном правиле.

История в `spec-authoring-workflow-user-stories.feature` сохраняет положительный сценарий корпуса. Его же использует штатная ветка кейса.

```gherkin
Feature: User stories
  @story:US-1
  Rule: Review before mutation
    Actor: Spec author
    Goal: Inspect the exact effect of a proposed edit.
    Benefit: Decide whether to approve the change before any target document changes.
    Outcome: review-preview | The author sees the full diff and the target hashes stay unchanged.
    ScenarioRef: review-preview | SCEN-proposal-preview-no-write

    @id:SCEN-proposal-preview-no-write @feature2 @AC-2.1
    Scenario: SPEC_AUTHORING_004 proposal previews a valid multi-document change without writing
      Given an immutable kernel snapshot and expected hashes for one specification
      When the caller proposes anchor-addressed edits to FR AC feature and task documents
      Then the result contains complete deterministic bounded diffs before and result hashes findings affected nodes proposal identity policy base snapshot and expiry
      And every repository document hash equals its pre-proposal hash
```

Кейс в `spec-authoring-workflow-use-cases.feature` добавляет ветку отказа и ссылается на уже записанный положительный сценарий.

```gherkin
Feature: Use cases
  @case:UC-2 @story:US-1
  Rule: Propose a traced multi-document change
    Actor: Spec author
    Boundary: Spec authoring MCP.
    Trigger: The author requests a preview of multi-document edits.
    Precondition: An eligible content-addressed kernel snapshot exists.
    Success: The author receives the complete bounded diff and every target hash stays unchanged.
    Step: submit | The author submits anchor-addressed edits and expected hashes.
    Step: validate | The service checks the proposed generation and its references.
    Branch: valid-preview | validate | The proposed change is valid. | The service returns the complete bounded diff and preserves target hashes. | end
    Branch: invalid-edit | validate | A broken anchor and missing requirement trace are found. | The service returns REJECTED with locations and leaves no stage or document change. | end
    ScenarioRef: valid-preview | SCEN-proposal-preview-no-write
    ScenarioRef: invalid-edit | SCEN-invalid-proposal-before-stage

    @id:SCEN-invalid-proposal-before-stage @feature2 @AC-2.2 @feature4 @AC-4.1
    Scenario: SPEC_AUTHORING_005 invalid proposal is rejected before staging
      Given a proposed generation contains a broken anchor and missing requirement trace
      When the proposal validator evaluates every mandatory lane
      Then the proposal becomes REJECTED with ordered field and location findings
      And apply refuses with no stage transaction journal audit persistence or document change
```

### Карта обязательных исходов

Единственный источник области задачи — раздел `## BDD coverage` в конце `ACCEPTANCE_CRITERIA.md`, с одним fenced-блоком JSON. В `outcomes` ключ исхода устойчив, `requirements` перечисляет связанные требования, `criteria` перечисляет критерии приёмки. `rule` и `outcome` указывают US и его `Outcome` либо UC и его `Branch`. Для системного исхода используется поле `scenario` вместо этих двух полей. Пример разрешается через `ScenarioRef`. Запись исхода сохраняется и при отсутствии этой ссылки. В `scopes` хранятся заранее выделенные области с точным набором требований и обязательных исходов. Каждое требование области имеет хотя бы один исход в ней. [Существующие критерии](../../tests/fixtures/kernel/real-corpus/.specs/spec-authoring-workflow/ACCEPTANCE_CRITERIA.md#L21)

В примере ниже только две строки утверждённой карты, связанные с областью `preview-validation`. У исходов полной `TASK-4` есть отдельные строки.

```json
{
  "schema": "omp-spec-kit/bdd-coverage@1",
  "outcomes": {
    "preview-diff": {
      "requirements": ["FR-2"],
      "criteria": ["AC-2.1"],
      "rule": "UC-2",
      "outcome": "valid-preview"
    },
    "invalid-edit-refused": {
      "requirements": ["FR-2", "FR-4"],
      "criteria": ["AC-2.2", "AC-4.1"],
      "rule": "UC-2",
      "outcome": "invalid-edit"
    }
  },
  "scopes": {
    "preview-validation": {
      "requirements": ["FR-2", "FR-4"],
      "outcomes": ["preview-diff", "invalid-edit-refused"]
    }
  }
}
```

Владелец проекта утверждает карту на канонической ветке `spec-<slug>` через `spec_patch(intent: "approveBddCoverage", map: …)`. Операция использует существующие предпросмотр и проверку снимка при записи. Hosted требует аутентифицированную роль `owner` из контекста сервера. Компилятор сохраняет карту в `ACCEPTANCE_CRITERIA.md` и добавляет каждому исходу `approvedSourceSha256`. Это хеш канонического JSON с содержимым связанных FR/AC и структурированными полями соответствующего исхода, включая условие, реакцию и выход для ветки UC. Пример выше показывает входную карту. Поля подтверждения пишет сервер. Обычный патч не может их добавить, заменить или удалить вместе с разделом. Версия карты — утверждённый Git-коммит и SHA-256 канонического JSON сохранённого раздела. Hosted читает утверждённые записи с канонической ветки проекта. Локальный MCP читает их из коммита, закреплённого владельцем в конфигурации запуска для этой спеки. При отсутствии утверждённой базы создание поведенческой задачи получает отказ. [Контекст полномочий сервера](../../src/service/dispatch.js#L197) · [Канонические refs](../../src/service/spec-branches.js#L134)

При допуске MCP пересчитывает `approvedSourceSha256` и `approvedExamples` на итоговом снимке. Для каждого зачтённого примера владелец утверждает конкретную ссылку `SCEN-ID` или `SCEN-ID#example_id` и хеш развёрнутых шагов, включая `Background`, аргументы шагов и подстановки из `Examples`. Карта допускает утверждение исхода до появления примера. Обычный авторинг может менять черновик и `ScenarioRef`. Обновлённый пример считается покрытием после утверждения его связи и содержимого. Замена `Then` под прежним ID лишает исход покрытия. Прогон для такого утверждения не требуется. Изменение в другой области не обнуляет допуск. При записи под блокировкой MCP снова сверяет исходную версию и итоговое состояние.

Hosted `spec_branch merge` сверяет защищённый раздел в каноническом родителе и в результате пробного слияния до push. Слияние с изменением защищённого раздела отклоняется. Владелец переносит решение через `approveBddCoverage` на канонической ветке. При отказе локальный checkout возвращается на исходный коммит, каноническая и рабочая ветки сохраняют свои вершины. Обычное слияние, которое сохраняет каноническую карту, проходит.

Для записи утверждения владелец передаёт `baseGenerationSha256` из предпросмотра в `repositoryRootFingerprint`. При смене снимка сервер возвращает конфликт. Для локального чтения зафиксированного решения переменная запуска `OMP_SPEC_KIT_APPROVED_COVERAGE_REFS` содержит JSON с ключом спеки и полным Git SHA. MCP-запрос использует доверенную базу из запуска процесса.

`confirmTaskCreation` и `create_task` используют `requirements` и необязательный `coverageScope`. Без `coverageScope` берётся объединение обязательных исходов всех требований. Каждое требование проверяется отдельно. При указанной области набор `requirements` должен точно совпасть с утверждённой записью. Область сохраняется в `TASKS.md` как `**Coverage scope:** preview-validation`. Те же проверки применяются к изменениям требований или области существующей задачи, включая `replace_task_links` и `replace_document`. Их вызываем по разнице полей до и после, поэтому правка комментария не меняет допуск. Отказ сообщает отсутствующий исход, FR/AC, правило и недостающий сценарий или строку. [Действующие поля создания задачи](../../src/authoring/proposals.js#L650)

## Приёмка четырёх исправлений

### Создание задачи с неполным BDD

На ревью собранная спека с FR, NFR, AC, дизайном, схемой и индексом требований получила L3 при нуле US, UC и сценариев. `SpecPatchService` принял `confirmTaskCreation` в режиме `dryRun`. Сейчас компилятор проверяет уровень и наличие подходящего требования. Контроль для нового допуска должен воспроизводить именно вызов создания. [Компилятор](../../src/authoring/proposals.js#L1086) · [Уровни готовности](../../src/kernel/readiness.js#L128)

Для выбранного допуска «по задаче» в срезе авторинга нужны следующие проверки.

- На L3 у поведенческой задачи без утверждённой карты MCP отказывает и запрашивает карту. Если карта есть, отказ перечисляет конкретные непокрытые исходы и связанные FR/AC и US/UC. Проверять все требования задачи. Ссылка на одно покрытое требование не закрывает второе.
- На двух согласованных исходах предпросмотра удалить из контрольного снимка описание ошибки с битым якорем. Положительный сценарий остаётся. Создание получает отказ с указанием `UC-2` и отсутствующего исхода `AC-4.1`. Возврат примера разрешает создание узкой задачи при нуле прогонов и пустой выборке `@spec-ready`. Пробел в несвязанном `UC-7` ей не мешает. Для полной `TASK-4` применить весь её согласованный перечень. [Два примера](../../tests/fixtures/kernel/real-corpus/.specs/spec-authoring-workflow/spec-authoring-workflow.feature#L36) · [Реальная задача](../../tests/fixtures/kernel/real-corpus/.specs/spec-authoring-workflow/TASKS.md#L34)
- Оба пути создания и оба пути изменения области проверяют итоговый граф. Правка, добавляющая ранее утверждённый пример и задачу, учитывает оба изменения. Подменённый `Then` при прежнем ID даёт отказ без записи. Обычный комментарий к задаче проходит. Прямая текстовая вставка нового ID в `TASKS.md` получает `TASK_DOCUMENT_BYPASS`. Предпросмотр и применение на одинаковом снимке дают одинаковый вердикт. [Нормализация создания](../../src/authoring/proposals.js#L650) · [Проверка прямой вставки](../../src/authoring/proposals.js#L1138)
- Обычный `writer` не может записать утверждённый раздел через полную замену `ACCEPTANCE_CRITERIA.md` или слияние. Проверка слияния включает положительный контроль для изменения вне защищённого раздела. Изменение исхода ветки или связанного критерия без утверждения блокирует задачу. Изменение несвязанного критерия сохраняет допуск. Повтор после утверждения владельцем проходит на новом снимке.

### Удаление одной истории или кейса

На двух соседних `Rule` текущая `removeEntityBlock` рассчитала замену, которая убрала также вторую историю с её сценарием. При отсчёте от первого тега остался синтаксически корректный пустой `Feature`. Так проявляется поиск следующего Markdown-заголовка для узлов US/UC. [Расчёт диапазона и вызов из deleteEntity](../../src/authoring/proposals.js#L559)

При переходе на Gherkin вычислять точный диапазон удаляемого правила по AST и исходным байтам. Включить собственные теги, описание, `Background`, сценарии и таблицы примеров этого правила. Для удаления одного сценария граница должна окончиться до тегов следующего сценария или правила. Сохранить исходные байты за пределами диапазона, включая комментарий соседа и переводы строк.

Критерий приёмки — в каждом из двух файлов расположить по два правила с разными ID, тегами и сценариями. Удалить первое через `deleteEntity`, затем на исходном снимке повторить для последнего. В diff и после применения должны исчезнуть только выбранное правило и принадлежащие ему сценарии. У соседа сверить байты, ID, строки `Examples` и связи. Для US с живым UC или для переиспользуемого сценария оставить ссылку в другом файле и получить отказ без записи, в том числе при `forceDelete`. Атомарная правка, переводящая ссылку на допустимую цель, проходит при целостном итоговом графе.

### Граница сценариев

Сценарии спецификации хранятся в двух Gherkin-файлах и описывают поведение. MCP проверяет синтаксис, связи и согласованное покрытие. Проверки релиза самого продукта находятся в `tests/features/release-contract.feature` и используют отдельные тестовые сценарии.

### Публикация уже выпущенной спеки

Для `ACTIVE`-спеки с ранее опубликованной `Version` замена трёх документов двумя меняет хеш дерева. Вызов `publishSpec` со старой версией и новым деревом вернул `VERSION_EXISTS`. Издатель берёт версию из `README.md` конкретной спеки. [Чтение версии и дерева](../../src/service/publish.js#L53) · [Защита опубликованной версии](../../src/service/publish.js#L98)

До конвертации сверить запись в журнале публикаций и Git-тег. Для уже выпущенной активной спеки зафиксировать новую свободную `Version` в плане переноса и записать её в `README.md` в том же коммите, что и новые файлы. Публикация выполняется с канонической ветки. При повторе использовать тот же целевой номер и проверять хеш дерева. Занятый номер с иным содержимым останавливает перенос этой спеки. Черновики сохраняют свой статус.

Приёмка через hosted `spec_documents(action: "read", version: …)` сравнивает `content`, `sha256`, опубликованный коммит и хеш каталога. Под прежней версией читаются три исходных документа с исходными хешами, под новой — оба Gherkin-файла с хешами переноса. Для уже перенесённой активной спеки обращение к удалённому старому имени сообщает об отсутствии файла и указывает каноническую пару. У ещё не перенесённой спеки обычное чтение старых документов разрешено. Повтор публикации того же результата сохраняет одну запись для целевой версии. Историческое чтение обращается к конкретному Git-объекту из журнала. Рабочий граф разбирает только новую раскладку. [Чтение версии](../../src/service/versioned.js#L96) · [Хеш в ответе](../../src/service/versioned.js#L137)

## Перенос одной спецификации при записи через MCP

Это решение заменяет общий перенос всех веток до запуска новой версии. 23 ноября 2026 года MCP проекта `stgmt/omp-spec-kit` показал 20 канонических спек в старой раскладке, 263 сценария в старом графе и ни одной рабочей ветки. Состав других проектов и веток определяется заново при каждом обращении. Переход не зависит от того, сколько остальных спек ещё ожидают переноса.

`spec_documents` читает старые исходники постранично, а `spec_patch intent: "migrateSpec"` выполняет preview/apply для одной выбранной спеки. Полный документ графа ограничен 8 МиБ; агрегат корпуса — 20 МиБ. Один профиль старого агрегатного предела 50 МиБ дал прирост RSS 311 808 000 байт — выше NFR-предела 201 326 592 байта. 20 измерений при 24 МиБ дали 194 215 936 байт, оставив 6,8 МиБ запаса. Предел 20 МиБ вмещает два предельных Gherkin-документа и 4 МиБ остальных документов спеки; профиль на этом пределе оставил 26,9 МиБ запаса. Обычное чтение допускает снимок до 64 МиБ и выдаёт страницы до 2 МиБ; hosted MCP принимает JSON-запросы до 24 МиБ, остальные JSON-маршруты сервиса сохраняют предел 4 МиБ. Крупное чтение через MCP сверяет снимок на каждой странице. [Чтение](../../src/adapters/document-service.js) · [Общий предел графа](../../src/kernel/limits.js) · [HTTP](../../src/service/http.js)

### Рабочая граница и состояние спеки

- Каноническая раскладка означает наличие обоих новых файлов и отсутствие трёх старых файлов в активном дереве. Состояние раскладки определяется отдельно от валидности содержимого. Если пара полная, но в ней ошибка Gherkin или нарушена обязательная ссылка UC на конкретную US, обычная диагностика показывает ошибку, а агент исправляет пару через `spec_patch`. Миграция для исправления не требуется.
- Если найден хотя бы один старый файл, неполная пара или одновременно старая и новая раскладки, конкретная активная спека требует миграции перед записью. Чтение остаётся доступным. Обе версии содержимого считаются источниками для сверки. Частично созданные новые файлы нельзя перезаписать или удалить без явного отражения в предпросмотре.
- Новый неинициализированный `spec_branch` может содержать один README и служебные метаданные до инициализации. Его `createSpec` должен атомарно создать пару, сохранив README и другие исходные данные. Существующую спеку с документами нельзя объявить новой пустой за счёт игнорирования её файлов. Для имеющегося пустого черновика миграция допускает пустые контейнеры `Feature`, когда источники подтверждают отсутствие историй, кейсов и сценариев.
- Обычное `spec_documents(action: "list" | "read")` перечисляет и читает существующие старые файлы конкретной спеки с её реальным содержимым. Обычные read-only запросы `spec_entities`, `spec_graph`, `spec_inspect`, `spec_tasks` и `spec_markdown` не отклоняются из-за старой раскладки. При неполном графе они возвращают доступные данные и явно показывают пределы результата, как описано ниже. Доступ к данным по-прежнему ограничен правами, проверками путей и обычными лимитами.
- Перед изменением содержимого, созданием задачи, публикацией, архивацией или другой изменяющей операцией конкретной активной спеки сервер проверяет её раскладку. Для старой или частичной раскладки запись отклоняется с причиной `LEGACY_SPEC_LAYOUT` или причиной неполной пары и машиночитаемым следующим действием для миграции. Это действует независимо от адресации по slug, ID, пути и `specSlugs`. Единственное изменение, разрешённое на этом этапе, — атомарный `migrateSpec`, результат которого соответствует канонической раскладке. Выдача или освобождение claim сами по себе не меняют документы и остаются доступны по обычным правилам прав.
- `dryRun: true` не записывает данные и доступен для подготовки изменений. Если предложенная обычная запись затронет старую спеку, preview показывает тот же блокер миграции и следующий шаг, что и `dryRun: false`; он не объявляет обычный apply разрешённым. Preview самой миграции работает по отдельному намерению `migrateSpec`.
- Создание новой спеки сразу использует новую пару. Обычные операции не создают и не переименовывают документы в старые имена, не обходят требование пары и не извлекают US/UC из Markdown как действующие сущности. Проверка выполняется на сервере независимо от хоста или hook.
- Явное чтение опубликованной версии через `version` и архивной спеки через `includeArchived` продолжает возвращать байты соответствующего неизменяемого снимка. Эти данные не добавляются в текущий граф и не меняют состояние активной спеки.

### Путь вызывающего агента

Реализованный контракт переиспользует обычные инструменты чтения и строго типизированное намерение `migrateSpec`. Схемы и инструкции опубликованы MCP-клиенту через `tools/list` и `initialize`.

1. Агент может заранее просмотреть спеку обычными `spec_documents(action: "list" | "read")` без миграции. При попытке записи в старую спеку отказ сообщает slug, затронутую ветку, найденные старые имена и способ переноса. Для подготовки переноса агент запрашивает `spec_documents(action: "list", spec: ..., includeSnapshot: true)`: перечень файлов выбранной спеки, размеры, хеши и идентификатор снимка. Hosted-снимок включает проект, ветку и commit HEAD. Локальный снимок привязан к составу и содержимому каталога. Состояние определяется по файлам и снимку, без отдельного маркера готовности, который может разойтись с ними.
2. Через обычный `spec_documents(action: "read", spec: ..., doc: ..., snapshot: ...)` агент получает исходное содержимое старых файлов и связанных FR, AC, README и других документов этой же спеки. Опциональный `snapshot` обеспечивает согласованность страниц и файлов для переноса; ответ содержит идентификатор снимка и хеш исходного файла, а изменившийся снимок даёт конфликт и требует нового inventory. Чтение без `snapshot` работает и вне миграции. При постраничном чтении должны сохраняться исходные UTF-8 байты и переводы строк, чтобы содержимое можно было точно сверить с хешем. Проверки проекта, прав, архивности, путей и ссылок файлов действуют на этом пути. Пользователь с правом чтения видит данные, а применение требует обычного права записи.
3. Агент составляет новые Gherkin-документы, карту соответствия прежних US/UC/SCEN новым правилам и строкам `Examples`, а также необходимые правки ссылок внутри этой спеки. Он передаёт через `spec_patch(intent: "migrateSpec", spec: ..., snapshot: ..., dryRun: true)` обычные `requestId` и `reason`, операции с содержимым новых и изменяемых документов и карту переноса. Для полного документа переиспользуется `replace_document`; удаление старых файлов формирует сервер в рамках миграции. Карта привязывает исходные файл, хеш и ID или диапазон к новым US/UC/SCEN и связям UC → US, а каждую строку исходной таблицы по её позиции — к `example_id`. Предпросмотр возвращает diff всех затронутых файлов, удаляемые старые имена, карту ID и ссылок, сохранённые исходные фрагменты, требуемые решения, результаты проверок и хеш предложения. Он не меняет файлы, refs, покрытие или задачи.
4. После проверки агент применяет тот же материал через `spec_patch(intent: "migrateSpec", ..., dryRun: false)` с проверенным snapshot и хешем предложения. Затем повторяет первоначальную попытку записи в эту спеку. При неоднозначной принадлежности сценария, отсутствующем существенном исходе или иной невыводимой из источников информации агент показывает конкретный источник и варианты владельцу. До решения предположения не записываются как согласованные требования.
   Не подтверждённое одноимённым исходным полем значение `Actor`, `Goal`, `Benefit`, `Independent Test`, `Boundary`, `Trigger`, `Precondition`, `Success`, `Covers`, `Step`, `Branch`, `Outcome` или `ScenarioRef` требует `fieldDecisions`: конкретные `entityId`, `field`, точное `value`, `reason` и исходный документ, хеш и диапазон строк из mapping этого же Rule. Старое значение нельзя скрыть в `Context` и выдать другое за исходное. Решения отображаются в preview и входят в его хеш; hosted-применение требует владельца.
   Для подтверждённого владельцем ремонта ошибочных шагов исходного Gherkin передаётся `repairs` с именем и SHA-256 исходника, `scenarioId`, диапазоном исходных строк, SHA-256 точных фрагментов до и после, текстом замены и причиной. Preview показывает оба фрагмента; решение связано с тем же snapshot и хешем предложения. Сервер допускает только непересекающиеся диапазоны строк шагов и проверяет исправленный текст официальным Gherkin-парсером. Остальные исходные строки, теги и таблицы остаются защищены сверкой; hosted-запись такого решения требует полномочий владельца.
5. Инструкции `mcp_preflight`, описания `spec_documents` и `spec_patch`, ответы с ошибкой и поставляемый навык объясняют агенту, что чтение доступно, а изменение старой спеки требует переноса. Чтение исходных файлов не возвращает старые US/UC в обычный граф как рабочую схему.

MCP передаёт закрытые схемы входов и ответов, стабильные причины отказа, ограничения страниц и предложений, выбранные project/topic и снимок. Это не позволяет незаметно переключить целевую спеку или ветку при продолжении миграции. Текст `initialize` описывает агенту чтение, блокировку записи, перенос, проверку preview, apply по хешу и повтор исходного действия.

Миграция меняет только выбранную спеку. Соседние спеки, даже если они ещё старого формата, не переписываются, не получают новые файлы и не считаются согласованными. Чтение старых документов не даёт права записывать прежнюю раскладку.

### Сохранность и проверка предложенного переноса

- Перенести каждую существующую историю, кейс, сценарий, ID, FR/AC-тег, `Refs`, описание, шаг, `Background`, таблицу и строку `Examples`. Сохранять приоритет, обоснование, условия и другие сведения исходных US/UC, используя структурированные поля и `Context` без выдуманных значений. История и кейс сохраняют связь. Сценарий находится в одном каноническом месте и может переиспользоваться через `ScenarioRef`; карта фиксирует все его исходные фрагменты, в том числе при совпадении старого и частично перенесённого содержимого.
- Для каждой старой строки `Examples` агент назначает уникальный устойчивый `example_id`. Сверка сравнивает исходные данные строк, включая неиспользуемые в шагах столбцы и повторы, а также результат подстановки в шаги. Изменение условия или результата требует отдельного показанного в diff решения. Официальный Gherkin AST используется и здесь; новый парсер схемы не вводится.
- Для спеки без историй или кейсов брать доказуемые сведения из её Feature и остальных документов. Пустой UC не создаётся ради заполнения шаблона. Системный `@contract` применим при наличии подтверждённого системного исхода и его FR/AC. Неоднозначный сценарий остаётся блокером переноса до решения, которое связывает его с допустимым владельцем.
- Сохранить существующие задачи, их статусы, требования и содержимое документов вне представленного diff. Миграция не утверждает новое покрытие автоматически и не выдумывает `@spec-ready`. Существующее согласование переносится только при доказанном соответствии идентификаторов и хешей согласованного содержания; иначе предпросмотр сообщает об устаревшем согласовании, а его обновление остаётся полномочием владельца.
- Входящие и исходящие межспековые ссылки не заставляют переносить весь корпус. Ссылки на FR/AC и другие доступные канонические сущности проверяются обычным графом. Если существующая ссылка указывает на US/UC/SCEN ещё не перенесённой спеки, сохранять её содержимое и происхождение, показывать её как ожидающую переноса целевой спеки и не считать подтверждённой. При переносе источника переписывать однозначно определяемые старые пути на канонические ссылки. Неоднозначные отображения показывать владельцу. Ссылки из других старых спек остаются в их исходных файлах и обрабатываются при обращении к ним. Для уже перенесённого источника с устаревшим путём после переноса цели показывать отдельную диагностику исправления, не изменяя источник автоматически.
- Новая ссылка на несуществующую или непроверяемую сущность остаётся ошибкой. Предпросмотр подтверждает происхождение каждой ожидающей ссылки по снимку и карте переноса; оставшиеся предупреждения включаются в базовую диагностику канонического дерева для сравнения при дальнейших правках. Существующая ожидающая ссылка не должна блокировать независимую правку уже перенесённой спеки, а полная проверка не должна объявлять её разрешённой. При последующем переносе целевой спеки повторно сверять ссылки и показывать несовпадения.

Перенос использует `readRepositorySpecs`, проверки путей, официальный Gherkin-парсер, граф и транзакции `spec_patch`. Полнота подтверждается предложением с source-to-target mapping и проверками миграции; отдельный `migrateSpecsToBranches` переносит каталоги по веткам и не конвертирует формат. [Проверка переноса](../../scripts/verify-gherkin-migration.mjs) · [Миграция веток](../../src/service/spec-migration.js#L30)

### Общие запросы по смешанному корпусу

- `spec_catalog(view: "specs" | "inventory" | "branches")` и preflight остаются доступны для проекта с любым числом старых спек. Они перечисляют каждую спеку и её состояние формата. Существующий список slug сохраняется; сведения о формате добавляются в согласованную схему ответа.
- Read-only запрос с явным набором slug возвращает доступные данные и состояние каждой запрошенной спеки, включая старые. Никакой запрос на чтение не инициирует перенос. Для записи агент переносит только конкретную изменяемую спеку.
- Поиск, статистика, board и трассировка доступны на смешанном корпусе. Из ещё не перенесённой спеки в граф попадают доступные сущности других документов; старые US/UC/SCEN не разбираются как канонические. Частичный ответ явно называет отсутствующие типы данных и затронутые спеки. Запрос по ID старой сущности сообщает, что её наличие в неполной области неизвестно, и указывает исходные документы; это не выдаётся за доказанное отсутствие сущности. Для `archivalProof` неполное чтение возвращает неподтверждённый результат, а последующая запись архивации отклоняется, если отсутствие входящих связей не доказано. Схемы, пагинация и fingerprint сохраняют эту информацию на каждой странице. Потребителей board и других запросов нужно обновить, чтобы они не трактовали частичный результат как полный.
- Обычная работа с перенесённой спекой не блокируется диагностикой другой старой спеки. При трассировке через такую спеку возвращается отметка о неполной границе и её slug. Известные ошибки самой выбранной спеки продолжают блокировать соответствующие операции.

### Транзакция и ветки

- `dryRun` и `apply` используют один компилятор предложения. Применение под существующей блокировкой повторно сверяет snapshot, hashes, права, claim и целевую ветку. Все новые файлы, правки ссылок и удаление старых файлов входят в одну восстанавливаемую транзакцию. Частичное дерево не выдаётся за готовое.
- В hosted режиме изменения попадают в один commit выбранной спеки и подтверждаются после успешного push. Если remote HEAD изменился с момента предпросмотра, вернуть конфликт и потребовать новый снимок. Автоматический rebase не должен незаметно применять миграцию к другим исходным байтам. Ошибка записи, commit или push оставляет восстановимое состояние и не сообщает об успешном переносе.
- Повтор того же `requestId` с тем же материалом после успеха, потери ответа или перезапуска возвращает подтверждённый результат без второго commit и удаления; тот же `requestId` с другим материалом получает конфликт. Локальный replay покрыт `tests/authoring-migration-replay.test.mjs`, hosted replay — `tests/service/migration-http.test.mjs` и `tests/service/active-migration-http.test.mjs`. Доказательство привязано к проекту, спеке, ветке, снимку и хешу предложения. [Журнал транзакции](../../src/authoring/transactions.js#L426) · [Запись в Git](../../src/service/writepath.js#L277)
- Каноническая ветка выбирается по slug. Если уже существует рабочая ветка старого формата, миграционный inventory и apply должны явно выбирать её topic и HEAD, не меняя каноническую ветку. Создание новой рабочей ветки из старой канонической сначала требует переноса канонической. Слияние проверяет итоговую пару и не теряет независимые правки старой рабочей ветки; конфликт возвращается агенту для разрешения через MCP.
- Для опубликованной ACTIVE-спеки предпросмотр показывает старую публикацию и требуемую новую свободную Version. При отсутствии нужного решения или полномочий применение останавливается с конкретным запросом. Повторная публикация, историческое чтение и ledger сохраняют прежнюю идентичность.

### Проверка по реальным путям

1. Поднять смешанный корпус из двух старых спек и одной канонической. Каталог показывает все три состояния. Обычные list и read первой старой спеки возвращают реальные старые файлы без переноса. Попытки создать задачу или изменить её документ получают блокер миграции без записи; preview показывает тот же блокер. Вторая старая спека остаётся побайтно и по Git HEAD неизменной.
2. Через настоящий MCP получить snapshot и выполнить обычный paged read, затем preview и apply переноса первой спеки. Проверить сохранение исходных байтов при постраничном чтении, сверить оба новых файла, исходные истории, кейсы, сценарии, таблицы, связи и сохранённые поля. Повторить первоначальную запись: блокер миграции исчезает, остальные правила записи проверяются как обычно. Результат одинаков для локального сервера и hosted HTTP.
3. Проверить исходники с отсутствующими US/UC, пустым черновиком, собственным `Background`, несколькими `Examples`, дублирующимися строками, неполной парой и одновременными старыми и новыми файлами. Для полной пары с ошибками проверить исправление через обычный `spec_patch` без ошибочного требования миграции. Ошибочные или неоднозначные соответствия не приводят к потере данных и не создают утверждённого покрытия.
4. Проверить старые и новые ссылки в обе стороны между перенесённой и неперенесённой спеками, реальные неверные ID, запрос по ID старой сущности, глобальный поиск, board и архивную проверку. Чтение возвращает доступные данные и признак неполноты, архивация не проходит без доказательства отсутствия входящих ссылок. Нет ложного полного графа и массовой блокировки независимой работы.
5. Проверить конкурентное изменение источника между чтением, preview и apply, смену remote HEAD, сбой commit/push, потерянный ответ, повтор и перезапуск. Транзакция атомарна, а повтор не перезаписывает новое содержимое и не создаёт второй commit.
6. Проверить ограничения reader/writer/owner, чужой проект, claim, запрещённые пути и symbolic links, рабочую ветку и версионное чтение. Операции MCP и `spec_branch merge` не позволяют вернуть старые имена или обойти проверку целевого формата. Прямую запись в файлы или Git push мимо сервиса MCP не перехватывает; если потребуется запрет и на этих путях, его нужно отдельно обеспечить в CI и настройках репозитория для изменяемых спек, не требуя перевода остальных.
7. Пилот выполнить на `spec-mcp-access-gate`. Проверить предложенную связь `UC-1 → US-1` и `SCEN-exact-authoring-allowlist`, затем обработать `blast-radius-auto-generation`, где отдельных старых файлов US/UC нет. Живые ветки остаются неизменными до отдельного согласованного применения.

## Удаление после проверки

- В исходниках и шаблонах удаляем генерацию `<slug>.feature`, старые канонические имена обоих Markdown-файлов, старые ветки Markdown-разбора US/UC и использование `<slug>.feature` для разрешения каталога. Удаляем `FEATURE` как единственный слот и правила хоста, завязанные на его имя. Старые имена используются для обычного чтения ещё не перенесённых исходников, в диагностике, сверке исторических версий и негативных тестах.
- Канонические активные фикстуры, demo, операторские runbooks и значения в release scripts переключаем на два файла. Замороженные публикуемые receipts и исходные снимки ранних релизов сохраняют сверяемые байты. Тесты самого продукта в `tests/features` и переиспользуемый протокол `SCEN-*/@AC` обслуживают свои контракты.
- Убираем план встроенных Markdown Gherkin-блоков как цель выпуска. Защиту транзакций, теги BDD и графовые ID переносим на два адреса.

- Упакованный stdio MCP прошёл чтение по byte-страницам и полный `migrateSpec` для исходного `USER_STORIES.md` размером 7,26 МиБ: preview, apply, точное совпадение текста после переноса и наличие `US-1` в построенном графе. Три старых файла удалены только после успешного apply; executable probe не запускался.
- Hosted HTTP MCP прошёл тот же перенос 7,26 МиБ с JSON-RPC preview/apply и Git read-back целевой ветки. Соседняя ветка осталась на прежнем HEAD. Отдельный запрос 5 МиБ прошёл HTTP JSON parser; предел MCP-маршрута составляет 24 МиБ, остальные JSON-маршруты остаются на 4 МиБ.
- `US-1 → FR-1 ← TASK-1` и `TASK-1 → FR-1 ← UC-1 → US-1` проверены настоящим `spec_graph` trace с `direction: "both"`, глубиной 2 и соответствующими типами рёбер. Новая схема рёбер для этих связей не вводилась.
- Скрипт [benchmark-large-spec-limit](../../scripts/benchmark-large-spec-limit.mjs) измеряет один документ на точном пределе 8 МиБ и корпус на агрегатном пределе 20 МиБ, по одному прогреву и 20 изолированным процессам на профиль. ### Проверка пригодности workflow для агента

- MCP `initialize` передаёт последовательность действий: прочитать legacy-документы, получить snapshot, подготовить `migrateSpec` с парой feature-файлов и source-to-target mapping, проверить preview, применить по `expectedProposalHash`, затем повторить исходную запись. `tests/mcp-protocol.test.mjs` закрепляет этот текст и схему инструмента.
- Полный реальный протокольный проход проверяется в `tests/dist-migration.test.mjs` и `tests/service/migration-http.test.mjs`: агентский клиент читает старую спеку, получает отказ на запись, переносит только её, повторяет исходную запись и проверяет результат. Тесты также убеждаются, что сценарии не выполняются и соседняя спека не меняется.
- Это проверка локальной собранной реализации на изолированных репозиториях, а не smoke-тест уже опубликованного MCP-хоста. Следующий minor-релиз и установленный у целевого агента сервер остаются последним незакрытым этапом.

Для реализации брать узкие наборы по затронутой области. Для парсера и графа — `tests/kernel-gherkin.test.mjs` и проверки затронутых типов. Для записи — `authoring-spec-lifecycle`, `gherkin-authoring-pilot` и `readiness-gate`. Для hosted — `tests/service/writepath.test.mjs` и `tests/service/publish.test.mjs`. Для поставки — проверка содержимого пакета, загрузка из чистого окружения и проверка доказательств релиза. Пробы и ревью описывают наблюдения на текущем коде. Положительные и отрицательные проверки целевого поведения входят в работу по соответствующим срезам.
